# Whole-project review and hardening — 2026-09-24

Written for the next Claude Code session. Read `CLAUDE.md` and
`docs/BUILD-STATE.md` first, then this. It records what a hostile review of the
whole repo found, what was fixed on branch `review-hardening`, what is still
open, and the decisions that must not be relitigated.

---

## The owner's standing rule from this session: SPEED FIRST

> "Whatever you suggest must not decrease the speed of uploading or any other
> functionality, because speed is the most important thing to me."

Every change is tagged **Faster / Neutral / One-off**. Anything that would slow
a hot path is dropped or flagged, not quietly traded. Speed claims are
**measured**, never asserted: vault paths with a before/after benchmark, and
pipeline changes against the 2026-09-19 drain baseline (6.6 GB: upload 9 min,
Check #2 fetch 12.5 min, hash+verify 4.5 min, idle 1.8 min, about 28 min). A
pipeline speed change ships as an **opt-in flag** (like `TG_PAR_FETCH`) that
stays off until a real drain measures it faster.

**Dropped because they would be slower. Do not re-propose without new evidence:**

| Idea | Why it was dropped |
|---|---|
| Encrypt footage before Telegram | An extra full read+write of every file on the 0-VPU block volume, plus CPU on 2 cores, plus a decrypt on every restore |
| Metrics HMAC in Python instead of `openssl` | A Python start-up every minute on the drain VM, for a low-value fix |
| Rewrite the bash uploader in Python | A risk to the only copy with no measured gain |
| Parallel *upload* | Already rejected in OPTIMISATION-PLAN: it writes to the archive, so a bug costs footage |

## What the review found

Three promises the system did not keep:

1. **The recovery code did nothing.** `unwrapKeyWithRecoveryCode` had no caller
   outside tests. The file key *was* PBKDF2(passphrase), so the passphrase could
   never change either.
2. **The docs claimed a CSP that was not deployed.** `proxy.ts` shipped
   `style-src 'unsafe-inline'`; SECURITY-NOTES said it didn't.
3. **The Insta360 ledger had no automatic backup.** `uploaded.sha256` is the only
   record of what Telegram holds; its only copy was a manual phone `scp`.

Plus, all verified in code and several against the live DB on 2026-09-24:

- anon/authenticated held **table-wide UPDATE on `user_keys`**, so a stolen
  session could overwrite `kdf_salt` and brick the vault (confirmed live)
- 4 unused `storage.objects` policies let a session upload **directly**,
  skipping the presign route's quota and size checks (confirmed live)
- the quota trusted the client-declared `size_bytes`
- the `filename_hash` blind index was salted with the server-stored `kdf_salt`,
  so it was dictionary-attackable, and nothing read it
- about 3× the file size in RAM on upload and download (iOS tab-crash risk)
- no sign-out; the decrypted list survived lock; `sw.js` was never registered;
  2 unused `@aws-sdk` dependencies; stale comments ("R2", "60 s", "one place")
- public sign-up UI on a single-owner vault (live `auth.users` = 1, so unused)
- metrics JSON built by heredoc, with only one string field escaped
- 0 tests on API routes, RLS or login, which is where all 4 production bugs were
- Actions pinned by tag; keepalive weekly against a 7-day pause window
- the README said "every original in two places"; the footage has **one copy**,
  in Telegram, and Telegram was missing from the budget ledger

## What was done (branch `review-hardening`)

| Area | Change | Speed |
|---|---|---|
| Keys | Envelope model in `lib/vault-keys.ts`: the data key is wrapped under the passphrase (new `passphrase_salt`, `passphrase_wrapped_key`) and the recovery code. "Forgot passphrase?" and "Change passphrase" screens (`components/PassphraseForms.tsx`). Legacy accounts upgrade in the background on first unlock. No file re-encrypted. | Neutral (one-off ~1 PBKDF2 in the background) |
| Transfer | `encryptBlob` reads the file chunk by chunk and prefetches the next; `decryptStream` decrypts as bytes arrive; the upload URL is fetched *during* encryption, since the ciphertext size is deterministic (`ciphertextSizeFor`). The wire format is unchanged, and tests prove both directions are compatible. | **Faster**: 50 MB upload 173→117 ms, peak +100→+12 MB; download 213→194 ms, +166→~0 MB |
| API | `/api/files` GET runs the list and the quota in parallel | **Faster** (one round trip fewer) |
| DB | `0005_least_privilege.sql`: drops the storage policies and `files` UPDATE; quota from `storage.objects`. `0006_passphrase_envelope.sql`: new columns, and `user_keys` UPDATE scoped to those two columns only. `0007_drop_filename_hash.sql`. | Neutral |
| CSP | `style-src 'self'; style-src-attr 'unsafe-inline'`. An e2e probe checks dynamic style attributes still apply on Chromium and WebKit; a negative control was run. | Neutral |
| UI | Sign-out on the Documents and Unlock screens; list cleared on lock; login is sign-in only | Neutral |
| Cleanup | `sw.js` and its test removed; `@aws-sdk/*` removed (27 packages); stale comments fixed | Neutral |
| Ops | The ledger in the nightly restic job (`immich-backup.sh`); metrics payload sanitised in place with bash namerefs (`json_str_vars` / `json_num_vars`, zero forks) | Neutral |
| Tests | Unit 66→115 (API routes 24, key management 17, streaming 12); e2e 140→142; `ops/metrics/test-payload-json.sh` (22); `supabase/tests/rls.test.sql` in the new `.github/workflows/rls.yml` | CI only |
| CI | Actions SHA-pinned; keepalive every 2 days; Python scripts byte-compiled in CI | CI only |
| Probe | `ops/insta360-bin/tg-probe-hashes.py`: a read-only test of whether Telegram's `upload.getFileHashes` can replace the Check #2 download | Could remove up to ~45% of drain time |

Docs updated: README (ledger, honesty line, recovery), SECURITY-NOTES (key
hierarchy, least privilege, CSP correction), RUNBOOK (ledger backup, Telegram
account hardening), BUILD-STATE (deploy order, verified counts).

## Incident found 2026-09-25 (branch `fix/backup-staging`)

`/status` showed critical. Diagnosed from the minute-level `metrics_samples` in
Supabase plus one read-only VM block (commands in RUNBOOK):

- **Backup failing since 2026-09-17.** restic backed up all of `/mnt/media`,
  including `tg-staging` (about 69 GB of footage that night; `*.insv` was not
  excluded). The repository reached **71,128 MiB against a 10,240 MiB tier**,
  and the guard then refused every night through a plain `exit 1`, which never
  fired the ERR trap. So the status froze and no alert was sent. Fixed:
  staging and `*.insv` excluded, and `refuse()` records the refusal and pings
  `/fail`. **The repository itself still needs shrinking**
  (RUNBOOK → "If the backup repository passes the free tier").
- **The drain hung for 6+ hours.** Check #2 by id hit Telegram
  `TimeoutError (GetFileRequest)` 12 times on a just-uploaded file, then fell
  back to downloading the whole **162 GB** channel onto about 111 GB free, at
  0.55 MB/s. Fixed: by-id retries after 120 s and 300 s, and the whole-channel
  fallback runs only if `full_channel_fits()` (fixture:
  `test-channel-fallback.sh`). Otherwise it fails with staging kept, and the
  drain retries.
- **Syncthing: two separate things, neither yet explained.**
  - **Disconnections are real.** `sync.connected` was false 21:10–23:30 IST on
    09-24, and for long stretches on 09-19. Android battery settings are the
    likely cause but are **unverified**.
  - **A genuine stall is real too.** `need_bytes` sat at 5.2 GB from 14:00 on
    09-19 until 18:00 on 09-24, including hours while the phone was connected,
    with nothing moving. Cause not yet found; the Syncthing journal for
    2026-09-19 is the next thing to read.
  - **CORRECTION.** An earlier version of this file said Syncthing "moved
    15 MB/s whenever connected". That was wrong. `staging_bytes` was `du` of all
    of `tg-staging`, *including* `.roundtrip`, so the 15 MB/s (and the
    0.55 MB/s) were the whole-channel **Telegram download** growing the scratch
    directory, not Syncthing. It proves nothing about Syncthing's speed. The
    collector now reports `roundtrip_bytes` separately.
  - `.roundtrip` sits inside the receive-only Syncthing folder, so the VM
    hashed GBs it never needs. `/.roundtrip` is now in the VM `.stignore`
    (done 2026-09-25).
- **One file Telegram stores but will not serve: ON HOLD, cause mapped.**
  `VID_20250221_145946_00_058.insv` (1,321,912,620 bytes, sha256
  `27fac9cb…6452289`) is parked in `/mnt/media/tg-hold/` (created with sudo,
  owned by ubuntu). **It is NOT in the ledger, so it stays on the camera card.**
  What `tg-probe-download.py` measured (read-only, 2026-09-25):
  - Messages 244 and 246 are two DISTINCT documents, so it was NOT
    de-duplication (that earlier guess was wrong).
  - Both fail at the SAME three 1 MiB blocks (626, 676, 1040 MiB), at EVERY
    request size down to 4 KiB; the other 1,259 blocks serve fine.
  - The blocks are ordinary video data (~99.6% non-zero), NOT zero padding
    (that guess was wrong too).
  - A scrambled copy (message 248, AES-CTR, reversible) served those three
    fine but died at two OTHER blocks (142, 892 MiB).
  - An old archived file (message 122, 1.87 GB, 09-17) serves all 1,784 blocks.
  - First reading ("new uploads land with random dead blocks, so re-upload
    small parts until clean") was **WRONG**. The first parts run disproved it:
    of 20 parts cut on 64 MiB (1 MiB-aligned) boundaries, 17 verified first
    time, and exactly the three holding the original dead blocks (.09, .10,
    .16) failed **six rounds running** (messages 258–283).
  - Reading that fits every observation: Telegram stores content-addressed
    1 MiB blocks, and a few stored blocks are broken. Any upload containing
    those exact aligned bytes maps to the broken block again, so re-uploading
    never helps. Different bytes per block (the scrambled copy) avoid them, but
    can hit other broken blocks. Unproven, but predictive.
  - **Fix: `tg-upload-parts.sh FILE`** uploads 64 MiB parts and verifies them
    with the parallel fetcher. A part failing twice is **reshaped**: its start
    moves +4 KiB, so every 1 MiB block in it holds different bytes. Only it and
    its predecessor are redone. The ledger row is written only when all parts
    verify, with a rejoin proof before any upload and after every reshape
    (fixtures: `test-upload-parts.sh`, including a content-bound failure case).
    Then `tg-delete-ids.py` removes 244, 246, 248 and the failed part copies.
    It refuses any id the ledger points at (`test-delete-ids.py`).
  - **Still open:** `restore.sh` downloads the WHOLE channel rather than by
    ledger ids, so one dead block anywhere stalls a full restore, and restore
    speed is the 0.64 MB/s sequential path. Restore-by-id (reusing
    `tg-fetch-par.py`) is the next fix. Also worth a periodic read-only scrub of
    every archived message with `tg-probe-download.py`.
- **Another process was working in this repo at the same time.** It committed
  `5953d5c` on `review-hardening` and auto-stashed uncommitted work
  ("wip: channel fallback (auto-stashed)"). Commit early; check `git stash list`
  if files seem to revert.

## Traps met this session

- **npm works in Bash after all:**
  `"/c/Program Files/nodejs/node.exe" "$LOCALAPPDATA/npm-standalone/node_modules/npm/bin/npm-cli.js" <args>`.
  npx still fails (EPERM on the cache), so download CLI binaries from GitHub
  releases instead (supabase 2.117.0, gitleaks 8.30.1, shellcheck 0.9.0 were
  fetched that way into the scratchpad).
- **Playwright's `webServer` calls `npm`**, which the shims break. Build with
  `node node_modules/next/dist/bin/next build`, start `next start -H 127.0.0.1
  -p 3000` in the background, then `node node_modules/@playwright/test/cli.js
  test`; it reuses the running server.
- **`expect(bytes).toEqual(...)` on megabytes takes minutes.** Compare with
  `Buffer.from(a).equals(Buffer.from(b))`, as the crypto suite already does.
- **A table-level `REVOKE` in Postgres also revokes column-level grants.** So
  every `user_keys` UPDATE statement lives in 0006 alone; a revoke anywhere else
  would silently undo it depending on apply order.
- **`python3` on this machine is the Microsoft Store alias.** `command -v`
  finds it but it doesn't run. Probe by running `python3 -c ''`.
- **Vite string aliases match `key + '/'`,** so the vitest alias key is `@`, not `@/`.
- **Vitest's `--poolOptions.forks.execArgv` hung the run.** Don't use it for benchmarks.
- **GitHub release downloads can crawl** (~20 KB/s). Use `curl -C - --max-time`
  to resume rather than a single long call.
